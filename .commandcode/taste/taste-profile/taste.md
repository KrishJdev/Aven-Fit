# Taste Profile
- Doc-first implementation: when asked to start a work unit or feature, consult the project's planning docs first — EXECUTION_PLAN.md for the plan, FEATURES.md/ARCHITECTURE.md for specs and rules, HANDOFF.md for current state — before writing any code. The user endorses this explicitly ("move on with the implementation of the next WU, refer to relevant docs for details") and repeats the same terse delegation every session ("move on with the implementation of the next WU, refer to relevant docs for details"; "go ahead with the implementation of the next WU"), expecting the full WU loop to run autonomously. Confidence: 0.95
- WU execution order: follow the EXECUTION_PLAN.md sequence strictly and defer the cross-cutting WUs (WU-X.1 Home Dashboard, WU-X.3 Progress Dashboard, WU-X.4 L6 states sweep, WU-X.5 schema/codegen sweep) until later per plan — deviate from the planned order only when absolutely necessary. Confidence: 0.9
- Gate WU starts on the user: wait for an explicit go-ahead before beginning the next WU — completing one WU (even with a HANDOFF "NEXT STEP" recorded) does not authorize auto-advancing to the next. Confidence: 0.9
- Treat the project's documented conventions as binding: each work unit lands as its own conventional commit (e.g., `feat(scope): ... (WU-X.Y)` with body bullets), HANDOFF.md gets a dated session summary (kept in chronological order) plus an explicit "NEXT STEP (exact)", and verification gates (codegen → `flutter analyze` → full `flutter test` passing) run before committing. Confidence: 0.85
- Phase completion gets a spec-completeness audit plus a full test battery: when a phase/milestone wraps, the user expects a review that nothing was missed ("do a full review of the P0 mvp to make sure that we didnt miss any features or implementation also do a full test for this phase") — read the spec (FEATURES.md) end-to-end, verify every priority-tagged item ([P0]) against the actual code and tests as complete/partial/missing (resolving uncertain details by grepping the implementation, not trusting the docs), then run the full multi-package battery for the phase: backend `./gradlew test` launched in the background in parallel with `flutter analyze && flutter test` in the foreground. Confidence: 0.7
- Review findings are fix-orders, not reports: when a spec-completeness audit or test battery surfaces a genuine defect — or even a minor spec deviation (naming format, a missing filter/sort control, a missing quick-info sheet, un-externalized strings) — the user expects it fixed in the same session ("continue with what error was found i want it fixed"; "fix these issues for now"), not merely ledgered in HANDOFF. Run each fix through the full WU loop (production fix, regression test, analyze + full-suite gates, dated HANDOFF record) before reporting back. Confidence: 0.85
- Scope each WU commit to the affected paths only (`git add HANDOFF.md mobile`), leaving unrelated working-tree changes unstaged. Confidence: 0.7
- Hold `flutter analyze` at 0 issues: fix even trivial pre-existing lint infos surfaced while working a WU rather than leaving them. Confidence: 0.8
- Windows shell: heredocs are unsupported — write multi-line commit messages to a temp file and commit with `git commit -F <file>`; Unix-only pipe utilities like `tail` are also absent, so chained commands such as `... 2>&1 | tail -5 && flutter analyze` fail mid-chain — run each gate command plainly as its own invocation instead. Confidence: 0.8
- Drift + Riverpod widget-test harness: use `UncontrolledProviderScope` and **drain before the fake-async body ends** — with a live drift stream subscription, `db.close()` in tearDown hangs forever (close awaits a stream-cleanup timer that can never fire once the body has ended; proven via print phase markers). The deterministic drain, root-caused empirically (WU-4.5 probes): unmount the tree (`pumpWidget(const SizedBox.shrink())`) → `container.dispose()` → `pump(...)` — encode it in the pump helper's `addTearDown`; `db.close()` then completes cleanly. Unmount+pump without dispose still hung in the probed configuration (though the older Home/session chain happens to pass undrained) — treat the full three-step drain as the default for any new stream-backed harness. Periodic `Timer`s add a second, harder constraint (found in WU-5.2, pinned via a throwaway probe): flutter_test checks the pending-timer invariant **before any addTearDown callback runs**, so a controller with a 1s tick cannot be drained from the pump helper's addTearDown at all — the drain must run in-body via a `testWidgets` wrapper's `finally` (the `authScreenTest` pattern), with the probe file deleted once the root cause is recorded in HANDOFF. Confidence: 0.9
- No hacks left behind: when a shortcut slips into the code mid-WU (e.g., a reflection-based `refOf(context)` helper to grab a WidgetRef from a stateless context), replace it with the proper idiomatic solution immediately rather than shipping it. Confidence: 0.65
- Platform-channel bridges gate native calls on `Platform.isAndroid` and register channel handlers lazily behind the gate: unmocked platform channels hang the flutter-test harness (discovered live in WU-3.10), so the gate is load-bearing for the entire suite; keep a `debugForceSupported`-style test seam for payload-verification tests. Confidence: 0.85
- Platform plumbing is fail-safe by design: every channel call is fire-and-forget, wrapped in `on MissingPluginException / on PlatformException / catch (_)`, and the native side forwards best-effort to a possibly-dead engine — notification/service work must never break core flows (L2). Confidence: 0.8
- Timers/countdowns are epoch-based, never accumulation: persist deadlines (epoch ms) and recompute displayed values each tick with pure arithmetic (L8, zero drift); Dart stays the single source of truth and native code (e.g., the foreground service) only renders pushed epoch fields and forwards actions. Confidence: 0.8
- Native Android work adds its own pre-commit gate: `gradlew :app:compileDebugKotlin :app:processDebugMainManifest` must pass (Kotlin compiles, manifest merges) alongside the build_runner/analyze/test gates. Confidence: 0.75

Confidence: 0.8

- Read-only questions get read-only answers: when the user asks an informational/progress question (e.g., "dont edit files just answer till what WU we have completed the dev"), answer from the project state — HANDOFF.md, git history, docs — with zero file edits or mutations. - Presentation laws for goal/score surfaces (FEATURES.md L4/L6): adherence-neutral by design — over-target days render neutral grey facts, never red/green judgment colors or alarms; unset data hides the whole card (meaningful absence) and omits percentage bars entirely (a percentage of nothing is a fake verdict); unknown values render "—", never a silent zero; empty states are designed ("Nothing logged yet."), not blank; the same unknown-semantics govern aggregates (pinned by the nutrition fiber test): an unknown-value item never contributes a silent zero to a sum — mixed days sum only the known values, and an all-unknown aggregate stays null, not 0. The L6 sweep (WU-X.4) completed the law: every async load renders a designed state — the static glass skeleton loader, not a bare spinner or animated shimmer (short local reads don't earn animation/battery cost) — and every error branch offers a recovery path (keyed RETRY wired to `ref.invalidate` of the exact failing provider; family providers invalidated with their argument) — an error is never a dead end. Confidence: 0.7
- Write-action failures keep the view alive with local error state — never a global collapse: don't wrap a finish/save action in `AsyncValue.guard`; a thrown write-through swaps the entire screen body into the load-error state whose RETRY offers the wrong action. Instead carry explicit flags in the state (`isSaving` marks the in-flight write and double-fire-guards the action, `errorMessage` is set on failure, the data itself untouched) and surface a designed recovery affordance — a floating snackbar with a keyed RETRY that re-runs the same action (§8.1 "save error with retry — data stays local, always recoverable"; complements L6, which governs load errors via `ref.invalidate`). Confidence: 0.7
